### FLUX status — new, more specific evidence this month; still not acted on

Last month's search returned directly contradictory claims and nothing was
changed. This month's searches are **more specific and mutually
consistent**, which is itself worth flagging even though I still didn't
act on it:

- Multiple independent sources (a dated MoneySavingExpert forum thread titled
  "Octopus Flux is open to new households again", plus review-site coverage)
  agree that **standard Octopus Flux reopened to new sign-ups on 16 September
  2026**, after being paused since March 2026.
- The same sources are consistent that **Intelligent Octopus Flux (the
  battery-automation variant) remains paused** — "Octopus says Flux will
  return when market conditions allow but hasn't given a timeline" refers
  specifically to the Intelligent variant.

**Why I still didn't touch `closedToNew` this month**: the current entry is
a single bare `"FLUX"` regex, which matches both variants' product codes (both
almost certainly contain the substring "FLUX"). If standard Flux is open and
Intelligent Flux is closed, the correct fix is to split this into two
regexes — but I don't know the actual Kraken product codes for either
variant (API access is blocked), so I can't write a precise split without
guessing. Guessing wrong here has asymmetric risk: incorrectly marking a
still-closed product as available is worse than the current state (both
hidden), since it could let the app present something as sign-up-ready that
Octopus will reject. Leaving `closedToNew` unchanged is the conservative
choice, but **this is now the single highest-value item for next review**:
once Kraken API access works, pull the product codes matching `FLUX` and
check their `available_from`/direction fields to write a precise two-way
split (see NEEDS APP-CODE CHANGES below).

## NEEDS APP-CODE / INFRA CHANGES

- **Network egress allow-list — STILL UNRESOLVED, now 4 months running.**
  Same ask repeated because nothing has changed; see root-cause section
  above for the specific domain list and the settings path (environment
  Network access). This is the actual blocker for everything else on this
  list and for steps 1–3 of the brief generally.
- **FLUX closedToNew regex needs splitting, with new urgency.** Evidence is
  now specific and dated (16 Sep 2026) that standard Octopus Flux reopened
  while Intelligent Octopus Flux did not. The current single `"FLUX"` source
  is almost certainly over-broad today, keeping a now-open product hidden in
  the apps. Needs the actual Kraken product codes for both variants (via the
  product API, currently blocked) before a precise regex fix can be written
  safely — do not guess a split from search results alone.
- **Scraper gap: retired adapter-owned ids aren't auto-tombstoned.** While
  manually performing the cap rollover this month (because the scraper
  itself couldn't fetch), I noticed `scraper/fetch-other-tariffs.mjs`'s
  per-adapter retirement logic (`byId.delete(id)` for each id in `owns`)
  removes a stale owned id from `tariffs` when the adapter's fresh output no
  longer includes it, but never adds that id to `removed`. Concretely: if
  `ofgemPriceCap()` ever returns only one period (no next-period id) after
  previously having emitted `svt-price-cap-next`, the id simply vanishes from
  `tariffs` without a tombstone, so apps that cached it client-side would
  never be told to delete it. I tombstoned `svt-price-cap-next` by hand this
  month per the file contract ("add an id here whenever you drop an entry"),
  but the scraper should do this automatically: track ids that go from
  present → absent across a run and add them to `removed`, not just the
  already-tombstoned-and-reemitted case it currently handles.
